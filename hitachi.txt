
Title: Add a SAN volume on Hitachi array using raidcom.
 Date: 09-Dec-2025
 Tags: admin, replication

Create new SAN volumes on the Hitachi array and map to a host. If any of the volumes are replicated, additional steps will be required to complete this task.


a) Review SAN storage configuration.

   Identify existing host volume LDEVs, name and size, if any exist.
     # cci-report.sh <serial> ldev <host>

   Check to see if this host has replicated volumes using Shadow Image or True Copy.
     # pairdisplay -g <group> -fcxe -CLI -I[SI|TC][Instance#]; or
     # pair-cmd.sh <serial> <host>


b) Create the new volumes.

   Identify next available LDEVs.
     # raidcom get ldev -ldev_list undefined -key front_end -pool_id 0 -fx -I[Instance#] > /var/tmp/<serial>-ldevs.txt
     # grep <NN>[0-9a-f][0-9a-f] /var/tmp/<serial>-ldevs.txt | head -<n>; or 
     # cci-report.sh [serial] used

   Identify next available Group ID for this HostGroup. (skip if server HostGroup already exists)
     # raidcom get host_grp -port <port> -I[Instance#]

   Create and name logical device. (select appropriate allocation type)
     # raidcom add ldev -ldev_id <ldev#> -capacity <size> -pool 0 -status disable_fullallocation -I[Instance#]; or
     # raidcom add ldev -ldev_id <ldev#> -capacity <size> -pool 0 -status enable_fullallocation -I[Instance#]
     # raidcom modify ldev -ldev_id <ldev#> -ldev_name <ldev name> -I[Instance#]

   Create new HostGroup and set mode based on host OS. (skip if server HostGroup already exists)
     # raidcom add host_grp -port <port> -host_grp_name <host group name> -I[Instance#]
     # raidcom modify host_grp -port <port> [<host group name>] -host_mode <host mode> -host_mode_opt <option> -I[Instance#]

   Add and provide a nickname for the HBAs to the new HostGroup. (skip if these already exist)
     # raidcom add hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -I[Instance#]
     # raidcom set hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -wwn_nickname <WWN nickname> -I[Instance#]

   Map logical device to HostGroup, using unique LUN.
     # raidcom add lun -port <port> [<host group name>] -ldev_id <ldev#> -lun_id <lun#> -I[Instance#]

   If replication is used, see "Create a Shadow Image" or "Create a True Copy".


c) Confirm new storage.
     # cci-report.sh <serial> ldev <host>


Notes:

 - The WWNs are formatted differently on the G1500 array vs. Brocade fabric switches. The colons must be removed when referencing WWNs on Hitachi storage arrays. The script cci-report.sh includes colons for ease of readability, and matching format used by sw-report.sh (the script used to extract SAN fabric information).

 - If data replication was configured for this host, you should see additional volumes with a "_si" or "_tc" suffix added to the volume label, used to quickly identify the S-VOLs or target volumes of replication pairs. The P-VOLs or source volumes do not use a suffix. Shadow Image S-VOLs are always located on the same array, but True Copy S-VOLs are not. For this reason, if host data is being replicated across Data Centers, True Copy will be used.

Title: Expand a SAN volume on Hitachi array using raidcom.
 Date: 09-Dec-2025
 Tags: admin, replication, grow, increase

Grow an existing host SAN volume on an Hitachi array. If the volume is replicated (using Shadow Image or True Copy), additional steps will be needed before and after the expansion step.

Note: Stripped volumes on Windows cannot be expanded. The data must be migrated onto a new set of stripped disks with additional capacity spread across all of the new disks.

a) Review SAN storage configuration.

   Identify the volume LDEV, name and size.
     # cci-report.sh <serial> ldev <host>

   Check to see if the volume is replicated using Shadow Image or True Copy.
     # pairdisplay -g <group> -fcxe -CLI -I[SI|TC][Instance#]; or
     # pair-cmd.sh <serial> <host>

   If the volume is replicated, continue to step (c).


b) Expand the volume.
     # raidcom extend ldev -ldev_id <ldev#> -capacity <size> -I[Instance#]

   Confirm new storage.
     # cci-report.sh <serial> ldev <host>

   Stop Here - Task completed.


c) Split the replication pair (required to enable volume expansion).

   Identify and verify that the size of the S-VOL matches the P-VOL. (optional)
     # cci-report.sh <serial> ldev <host>

   If Shadow Image or True Copy is being used, destroy the replication pair.
     # pairsplit -g <group> [-d <pair vol>] -S -I[SI|TC][Instance#]; or
     # pair-cmd.sh <serial> <host>

     # pairdisplay -g <group> -fcxe -CLI -I[SI|TC][Instance#]; or
     # pair-cmd.sh <serial> <host>


d) Expand the volumes.

   Expand each pair volume (P-VOL and S-VOL).
     # raidcom extend ldev -ldev_id <ldev#> -capacity <size> -I[Instance#]

   Confirm new storage of each pair volume (P-VOL and S-VOL).
     # cci-report.sh <serial> ldev <host>


e) Re-create the replication pair (if previously PAIRed).

   For Shadow Image volumes...
     # paircreate -g <group> [-d <pair vol>] -vl -c 15 -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>

   For True Copy volumes... 
     # paircreate -g <group> [-d <pair vol>] -vl -c 15 -fg never [CTGID] -ITC[Instance#]; or
     # pair-cmd.sh <serial> <host>

   Confirm the pair status is PAIRed for every member of the device group name.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>

Notes: 

 - Specify the amount to grow or expand by, not the end result.

 - Use the pair-cmd.sh script to determine the HORCM Instance and Consistency Group (CTGID, required for True Copy) for the pair commands. Select pairsplit or paircreate options to get this information, along with actual commands to run.

 - All replication P-VOLs have an even HORCM Instance value, S-VOLs an odd value. This is especially helpful when examining True Copy volumes and their replication direction. Not all replication is from Mercy Drive to Sun Trust.

Title: Delete a SAN volume on Hitachi array using raidcom.
 Date: 25-Nov-2020
 Tags: admin, reclaim, remove, decommission, Shadow Image, True Copy, shadowimage, truecopy

Delete a host SAN volume from the Hitachi array. If any of the volumes being deleted use replication (via Shadow Image or True Copy), then additional steps will be required. A change ticket is required, and must be approved by CAB before proceeding.


a) Review SAN storage configuration.

   Identify existing host volume LDEVs, name and size, if any exist.
     # cci-report.sh <serial> ldev <host>

   Identify the HostGroup and pWWNs for this host.
     # cci-report.sh <serial> hostgrp <host>

   Check to see if this volume is being replicated using Shadow Image or True Copy.
     # pairdisplay -g <group> -fcxe -CLI -I[SI|TC][Instance#]; or
     # pair-cmd.sh <serial> <host>

   If the volume is replicated, see "Delete a Shadow Image", "Delete a True Copy".


b) Unmap the volumes from the old HostGroup ports.

   Delete logical device from HostGroup, using logical device ID.
     # raidcom delete lun -port <port> [<host group name>] -ldev_id <ldev#> -I[Instance#]


c) Delete the volume.
     # raidcom delete ldev -ldev_id <ldev#> -I[Instance#]

   Verify the volume was removed.
     # cci-report.sh <serial> ldev <host>


Notes: 

  If the volume belongs to a VMware host, please notify the VMware Team in advance, so the alerts which are normally generated would be expected. They will perform a storage rescan afterwards to cleanup any dead LUNs.

Title: Retire host from Hitachi array using raidcom.
 Date: 06-Mar-2019
 Tags: admin, delete, reclaim, remove

Removing a host from Hitachi array is usually done during the cleanup phase of de-commission work. This effectively removes all of it's allocated storage on the array, allowing this space to be reclamed. A check should be made prior, to verify the host has been shutdown, as indicated by the switch reporting that these pWWNs are no longer present, and the switch port is offline (unless virutalized behind another server), before proceeding. Make sure the host is removed from the SAN fabric, if no other SAN storage for this host is still in use.


a) Review SAN storage configuration.

   Identify existing host volume LDEVs, name and size, if any exist.
     # cci-report.sh <serial> ldev <host>

   Identify the HostGroup and pWWNs for this host.
     # cci-report.sh <serial> hostgrp <host>

   Check to see if this volume is being replicated. Confirm with one of the commands below.
     # pairdisplay -g <group> -fcxe -CLI -I[SI|TC][Instance#]; or
     # pair-cmd.sh <serial> <host>

   If the volume is replicated, see "Delete a Shadow Image", or "Delete a True Copy".


b) Delete the host volumes.

   Delete logical device from HostGroup, using logical device ID. (remove from both HostGroup ports)
     # raidcom delete lun -port <port> [<host group name>] -ldev_id <ldev#> -I[Instance#]

   Delete host HBAs from the HostGroup. (check both HostGroup ports)
     # raidcom delete hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -I[Instance#]

   Delete the HostGroup port. (remove both HostGroup ports)
     # raidcom delete host_grp -port <port> [<host group name>] -I[Instance#]

   Delete the volumes.
     # raidcom delete ldev -ldev_id <ldev#> -I[Instance#]


c) Verify storage was deleted.
     # cci-report.sh <serial> ldev <host>


Notes:

 - The WWNs are formatted differently on the Hitachi array vs. Brocade fabric switches. The colons must be removed when referencing WWNs on Hitachi storage arrays. The script cci-report.sh includes colons for ease of readability, and matching format used by sw-report.sh (the script used to extract SAN fabric information).

 - If the volumes belong to a VMware host, please notify the VMware Team in advance, so the alerts which are normally generated would be expected. They will perform a storage rescan afterwards to cleanup any dead LUNs.

Title: Create a Shadow Image on Hitachi array using raidcom.
 Date: 08-Dec-2025
 Tags: admin, replication, create, shadowimage

Shadow Image is used to create a Point-in-Time copy of host volumes within a single Hitachi storage array. The steps below describe the process. An alternate method is also available via the build-pairs.sh script, which automates the process. Follow this guide when creating a new Shadow Image, or adding volumes to an existing Shadow Image.


a) Review SAN storage configuration.
     # cci-report.sh <serial> ldev <host>

   Review the replication configuration.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>

   If a device group already exists for this host, then stop here.


b) Create the replication volumes.

   Identify next available LDEVs.
     # raidcom get ldev -ldev_list undefined -key front_end -pool_id 0 -fx -I[Instance#] > /var/tmp/<serial>-ldevs.txt
     # grep NN[0-9a-f][0-9a-f] /var/tmp/<serial>-ldevs.txt | tail -<n>; or
     # cci-report.sh [serial] used

   Identify next available Group ID for this HostGroup.
     # raidcom get host_grp -port <port> -I[Instance#]

   Create and name the new volumes. (select appropriate allocation type)
     # raidcom add ldev -ldev_id <ldev#> -capacity <size> -pool 0 -status enable_fullallocation -I[Instance#]; or
     # raidcom add ldev -ldev_id <ldev#> -capacity <size> -pool 0 -status disable_fullallocation -I[Instance#]
     # raidcom modify ldev -ldev_id <ldev#> -ldev_name <ldev name> -I[Instance#]

   Create new HostGroup and set mode based on host OS. (skip if HostGroup already exists)
     # raidcom add host_grp -port <port> -host_grp_name <host group name> -I[Instance#]
     # raidcom modify host_grp -port <port> [<host group name>] -host_mode <host mode> -host_mode_opt <option> -I[Instance#]

   Add and provide a nickname for the HBAs to the new HostGroup. (skip if HBA WWNs and nicknames already exist, or S-VOLs are not mapped to another server)
     # raidcom add hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -I[Instance#]
     # raidcom set hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -wwn_nickname <WWN nickname> -I[Instance#]

   Map logical device to new HostGroup port, using unique LUN.
     # raidcom add lun -port <port> [host group name] -ldev_id <ldev#> -lun_id <lun> -I[Instance#]

   Verify the new volumes (P-VOLs and S-VOLs).
     # cci-report.sh <serial> ldev <host>


c) Update the HORCM configuration.

   Add the Host dev group to the HORCM_LDEV and HORCM_INST sections.

   Edit the HORCM file used to define P-VOLs.
     # vi /etc/horcm<#>.conf

     HORCM_LDEV
     #dev_group                      dev_name        Serial#     CU:LDEV(LDEV#)     MU#
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0

     HORCM_INST
     #dev_group                      ip_address      service
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  XXXXXXXXXXXXXX  NNNNNN


   Edit the HORCM file used to define S-VOLs.
     # vi /etc/horm<# + 1>.conf

     HORCM_LDEV
     #dev_group                      dev_name        Serial#     CU:LDEV(LDEV#)     MU#
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0

     HORCM_INST
     #dev_group                      ip_address      service
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  XXXXXXXXXXXXXX  NNNNNN

   Note: horcm files are located on lpr-hdsprb-ap01 or lpr-hdsprb-ap02, and edited using the saninfo account.


d) Restart HORCM and verify changes.
     # horcmshutdown.sh <#> ...
     # horcmstart.sh <#> ...

   Validate HORCM configuration changes.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>

   Note: horcmstart.sh and horcmshutdown.sh must be run from the saninfo account.


e) Create the replication pair.
     # paircreate -g <group> [-d <pair vol>] -vl -c 15 -ISI[Instance#]

   Confirm the pair status is PAIRed for every member of the device group name.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>


Notes:

 - The WWNs are formatted differently on the Hitachi array vs. Brocade fabric switches. The colons must be removed when referencing WWNs on Hitachi storage arrays. The script cci-report.sh includes colons for ease of readability, and matching format used by sw-report.sh (the script used to extract SAN fabric information).

 - If Shadow Image had been previously configured for this host, you should see two sets of volumes for this host, P-VOLs and S-VOLs. The Shadow Image volumes (S-VOLs) can be identified by their "_si" suffix, and should each have the same capacity as each (P-VOL) counterpart, using the same LUN.

 - The MU# entry within the HORCM config file for P-VOLs defines the Shadow Image copy number, starting with 0 for the initial copy. Increment this for each successive copy of the same P-VOLs, up to MU#2. The Shadow Image SVOLs must always use MU#0.

 - If any host pairs are missing from the HORCM configration, create the missing S-VOL volumes, using the guidelines above. Update the HORCM files (/etc/horcm[N].conf, /etc/horcm{N+1].conf) before proceeding.

 - Create, Suspend, Split, or Delete pairs using the appropriate pair command, checking the pair status afterwards using pairdisplay. The pair-cmd.sh script simplifies this using menus, as well as providing command syntax and examples.

 - Coordinate with the Sys Admin on when creating the Shadow Image (Point-in-Time image), in order to guarantee a clean copy.

Title: Refresh a Shadow Image on Hitachi array using raidcom.
 Date: 17-Jan-2019
 Tags: admin, replication, create, shadowimage

Shadow Image is used to create a Point-in-Time copy of host volumes within a single Hitachi storage array. The steps below describe the process to refresh an existing Shadow Image, ie. one where the data was captured, but no longer useful. The pairs are in the PSUS/SSUS or SMPL/SMPL state. An automated method is available to perform this task, using the build-pairs.sh script. Follow this guide when refreshing the Shadow Image for a host.


a) Review SAN storage configuration.
     # cci-report.sh <serial> ldev [Host]

   Review the replication configuration.
     # pairdisplay -g <Dev_Group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> [host]


b) Before the Change Control event.

   If any volume pairs have a status of SMPL, then re-create that pair...
     # paircreate -g <Dev_Group> [-d <Dev_Name>] -c 15 -vl -ISI<Instance>

   Otherwise, resync the pairs...
     # pairresync -g <Dev_Group> -ISI<Instance>

   Confirm pair status is PAIRed for every member of the Dev_Group.
     # pairdisplay -g <Dev_Group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> [host]


c) During the Change Control event.
     # pairsplit -g <Dev_Group> -ISI[Instance]

   Confirm pair status is SPLIT for every member of the Dev_Group.
     # pairdisplay -g <Dev_Group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> [host]


Notes:

  Coordinate this activity with the OS Admin, and any other parties affected, due to the requirement that the host is shutdown to guarantee a clean copy, ie. all pending writes had been flushed to disk.

Title: Restore a Shadow Image on Hitachi array using raidcom.
 Date: 09-Dec-2025
 Tags: admin, replication, shadowimage

When restoring host data from a Shadow Image, proceed with caution, as this will overwrite the original volumes! Confirm this request, ie. the host or application name, and one or more LDEV IDs with the Sys Admin before proceeding. Capture this confirmation via email or IM, for additional verification. 


a) Review SAN storage configuration.
     # cci-report.sh <serial> ldev <host>

   Review the replication configuration.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>


b) Verify a valid Shadow Image is available.

   Confirm the pairs have been split, ie. status is PSUS and SSUS for every Pair Volume in the device group.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>

   If this is not true, stop. A restore is not possible. 


c) Restore from the Shadow Image.

   Confirm the S-VOLs are not mounted, or that the host has been shutdown before proceeding.

   Restore the original volumes to the Point-in-Time of the last pairsplit operation.
     # pairresync -g <group> -restore -fq quick -c 15 -ISI[Instance#]


d) Re-enable normal I/O access to the P-VOLs following restore.

   Wait until the pair status shows PAIR for every Pair Volume in the group.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>


Notes: 

 - The pair volumes for this host must show a status of PSUS or SSUS.

 - The host must be shutdown, since during the restore process, these volumes will be in R/O mode.

 - Verify with the Sys Admin the hostname and volumes (by LDEV, Size and/or LUN) before starting.


Helpful Hint:

  Use the pair-cmd.sh script to review current pair status and/or generate pair commands on demand.

Title: Delete a Shadow Image on Hitachi array using raidcom.
 Date: 09-Dec-2025
 Tags: admin, remove, replication, shadowimage

Delete a host Shadow Image once either the copy is no longer needed, or a restore was completed successfully. As a general rule, stale Shadow Image pairs, ie. those suspended for more than a few days loose their value, and should be removed to free up storage space, and Shadow Image license capacity. This process is not destructive, as the original host volumes are not affected. Follow this guide when reclaiming one or more host volumes within a Shadow Image group, or when deleting the group entirely.


a) Review the replication configuration.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>


b) Delete the Shadow Image pair relationship.

   If the pair status is not SMPL every Pair Volume wihin the device group, do the following...
     # pairsplit -g <group> -S -ISI[Instance#]

   Confirm the pair state change.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>


c) Update the HORCM configuration.

   Remove the Host dev group from the HORCM_LDEV and HORCM_INST sections.

   Edit the HORCM file used to define P-VOLs.
     # vi /etc/horcm<#>.conf

     HORCM_LDEV
     #dev_group                      dev_name        Serial#     CU:LDEV(LDEV#)     MU#
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0

     HORCM_INST
     #dev_group                      ip_address      service
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  XXXXXXXXXXXXXX  NNNNNN


   Edit the HORCM file used to define S-VOLs.
     # vi /etc/horm<# + 1>.conf

     HORCM_LDEV
     #dev_group                      dev_name        Serial#     CU:LDEV(LDEV#)     MU#
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  NNNN-NNNN       NNNNNN          NN:NN           0

     HORCM_INST
     #dev_group                      ip_address      service
     XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX  XXXXXXXXXXXXXX  NNNNNN


   Note: horcm files are located on lpr-hdsprb-ap01 or lpr-hdsprb-ap02, and must be edited using the saninfo account.


d) Restart HORCM and verify changes.

     # horcmshutdown.sh <#> <#+1> ...
     # horcmstart.sh <#> <#+1> ...

   Validate HORCM configuration changes.
     # pairdisplay -g <group> -fcxe -CLI -ISI[Instance#]; or
     # pair-cmd.sh <serial> <host>

   Note: horcmstart.sh and horcmshutdown.sh must be run using the saninfo account.


e) Identify the Shadow Image S-VOLs to be deleted.
     # cci-report.sh <serial> ldev <host> si


f) Delete the Shadow Image S-VOLs volumes.

   Delete logical device from HostGroup, using logical device ID. (remove from both HostGroup ports, if no volumes remain)
     # raidcom delete lun -port <port> [<host group name>] -ldev_id <ldev#> -I[Instance#]

   Delete the HostGroup port. (remove both HostGroup ports, if no volumes remain)
     # raidcom delete host_grp -port <port> [<host group name>] -I[Instance#]

   Delete the volumes.
     # raidcom delete ldev -ldev_id <ldev#> -I[Instance#]

   Verify the volumes were removed.
     # cci-report.sh <serial> ldev <host>


Notes:

 - There should be two sets of volumes on the same storage array for this host. The Shadow Image volumes (S-VOLs) are identified by their "_si" suffix, and should have the same capacity as their source (P-VOL) counterparts, with the same LUN values.

 - The host volume pairs are defined within the HORCM configration (/etc/horcm[N].conf and /etc/horcm[N+1].conf, and need to be removed.

 - Check the pair status after each pair operation, to confirm the change was successful.

 - Use the appropriate HORCM Instance for all raidcom commands (Mercy Drive G1500 = 1, Sun Trust G1500  = 2, Mercy Drive E1090 = 10, Sun Trust E1090 = 11).

 - If any of the S-VOLs belong to a VMware host, please notify the VMware Team in advance, so the alerts which are normally generated would be expected. They will perform a storage rescan afterwards to cleanup any dead LUNs.


Helpful Hint:

  Use the pair-cmd.sh script to review current pair status and/or generate pair commands on demand.

Title: Create a True Copy between two Hitachi arrays using raidcom.
 Date: 08-Dec-2025
 Tags: admin, add, replication, truecopy

True Copy is used to create a Synchronous copy of host volumes between two Hitachi storage arrays, typically located in separate data centers. The steps below describe the process. Follow this guide when creating a new True Copy group, or adding volumes to an existing True Copy group.


a) Review SAN storage configuration.

   Identify existing host volume LDEVs, name and size, if any exist.
     # cci-report.sh <serial> ldev <host>

   If True Copy was configured prior, verify that a pair exists for every volume of this host.
     # pairdisplay -g <Dev_Group> -fcxe -CLI -ITC[Instance#]; or
     # pair-cmd.sh <serial> status


b) Create the new True Copy S-VOL volumes.

   Identify next available LDEVs.
     # raidcom get ldev -ldev_list undefined -key front_end -pool_id 0 -fx -I[Instance#] > /var/tmp/<serial>-ldevs.txt
     # grep <NN>[0-9a-f][0-9a-f] /var/tmp/<serial>-ldevs.txt | head -<n>; or
     # grep <NN>[0-9a-f][0-9a-f] /var/tmp/<serial>-ldevs.txt | tail -<n>; or 
     # cci-report.sh [serial] used

   Create and name logical device. Add a "_tc" suffix to the S-VOL names.
     # raidcom add ldev -ldev_id <CU:LDEV> -capacity <Size> -pool 0 -status disable_fullallocation -I[Instance#]
     # raidcom modify ldev -ldev_id <CU:LDEV> -ldev_name <LDEV_Name> -I[Instance#]

   Create new HostGroup and set mode based on host OS. (skip if HostGroup already exists)
     # raidcom add host_grp -port <Port#> -host_grp_name <Host_Group_Name> -I[instance#]
     # raidcom modify host_grp -port <Port#> [<Host_Group_Name>] -host_mode <Host_Mode> -host_mode_opt <Option> -I[Instance#]

   Add and provide a nickname for the HBAs to the new HostGroup. (skip if HBA WWNs and nicknames already exist)
     # raidcom add hba_wwn -port <Port> [<Host_Group_Name>] -hba_wwn <WWN_Strings> -I<Instance>
     # raidcom set hba_wwn -port <Port#> [<Host_Group_Name>] -hba_wwn <WWN_Strings> -wwn_nickname <WWN_Nickname> -I<Instance>

   Map logical device to HostGroup, using unique LUN.
     # raidcom add lun -port <Port#> [Host_Group_Name] -ldev_id <CU:LDEV> -lun_id <LUN> -I[Instance#]


c) Confirm new storage and verify volume sizes are identical.

   Perform this each storage array.
     # cci-report.sh <serial> ldev <host>


d) Update the HORCM configuration.

Title: Failover host between DCs with True Copy on Hitachi arrays using raidcom. (non-DR)
 Date: 18-Jan-2019
 Tags: admin, DR, replication, truecopy

Perform a scheduled failover, so that the production application running on the original host could be moved to a new host located at the alternate data center. The application and host need to be shutdown during the transfer, which normally takes a few seconds to complete. Most of the time required is consumed shutting down and restarting the application and OS.


a) Display the pair status.
     # pairdisplay -g <group> -fcxe -CLI -ITC[Instance#]; or
     # pair-cmd.sh <serial> <group>

   Note: The pair status should show PAIR for every pair within the Group.

b) Confirm with the Sys Admin that both the local and remote host have been shutdown before proceeding.

c) Swap replication direction between P-VOL and S-VOLs.
     # horctakeover -g <group> [-d <pair Vol>] -t 300 -ITC[Instance#]

   Note: The command must be run from the the array where the host will be located (as indicated by the HORCM Instance in ITC[Instance#]). Look for the following response to indicate the correct instance was used. No response is generated with the wrong instance, as the command simply aborts.

     horctakeover : Swap-Takeover done.

d) Display the pair status.
     # pairdisplay -g <group> -fcxe -CLI -ITC[Instance#]; or
     # pair-cmd.sh <serial> <group>

   Note: The pair status should be PAIR for every pair, with the P-VOL and P-VOLs roles reversed.

e) Start the new host.


Notes:

  The horctakeover command appears to automatically split the paired volumes, reverse the P-VOL and S-VOL ldevs, and resync in the opposite direction. All further pair operations from this point forward, ie. pairsplit, pairresync, etc. will continue to replicate in the new direction. New paircreate operations must be run from the new array management console, to guarantee the same replication direction is used.

Title: Failover host between DCs with True Copy on Hitachi arrays using raidcom. (DR)
 Date: 10-Mar-2020
 Tags: admin, DR, replication, restore, truecopy

Perform a scheduled failover, so that the production application running at datacenter1 could be moved to datacenter2 at the remote location. Maintain a backup copy of the host at datacenter1, in case a quick failback is needed return to the prior state. The application and host must be shutdown initially, to capture the complete copy, ie. all writes in memory have been flushed to disk. This takes only a few seconds to complete. 


1. Perform host failover from datacenter1 to datacenter2.

   a) Shutdown the host at datacenter1.

   b) Split pair replication, and allow R/W access to the host at datacenter2.
        # pairsplit -g <group> [-d <pair Vol>] -rw -ITC[Instance#]

   c) Confirm the pair state change is PSUS/SSUS.
        # pairdisplay -g <group> -fcxe -CLI -ITC[Instance#]; or
        # pair-cmd.sh <serial> <host>

   d) Start the host at datacenter2.

   e) Select option (2) or (3), depending on desired outcome.


2. Failback to the host at datacenter1, ignoring changes while at datacenter2.

   a) Shutdown the new host.

   b) Start the original host.

   c) Resume replication to secondary volumes.
        # pairresync -g <group> [-d <pair Vol>] -c 15 -ITC[Instance#]

   d) Confirm the pair state change is PAIRed.
        # pairdisplay -g <group> -fcxe -CLI -ITC[Instance#]; or
        # pair-cmd.sh <serial> <host>

   e) Stop here.


3. Remain at datacenter2, and restart replication from datacenter2 to datacenter1.

   a) Confirm the host at datacenter1 has been shutdown.

   b) Perform reverse resync (from secondary to primary volumes).
        # pairresync -g <group> [-d <pair Vol>] -c 15 -swaps -ITC[Instance#]

   c) Confirm the pair state changes to PAIRed.
        # pairdisplay -g <group> -fcxe -CLI -ITC[Instance#]; or
        # pair-cmd.sh <serial> <host>

   d) Stop here.


Caution:

- Note the direction of replication before proceeding with any True Copy operation, to avoid replicating in the wrong direction. If P-VOLs are identified as Local volumes using pairdisplay, then this array contains the source, or P-VOLs. The pair-cmd.sh status option can be used to show replication direction.


Notes:

 - During step 1, the host data at datacenter1 remains intact, allowing a failback to the previous Point-In-Time when that host was shutdown.

 - Once True Copy replication starts, all changes to the host data at the other datacenter (where the host is shutdown) will be lost.

 - During True Copy replication, the target host volumes are limited to R/O access, ie. do not attempt to boot that host using these volumes.

 - Switching the replication direction using a reverse resync changes all P-VOLs to S-VOLs, and all S-VOLs to P-VOLs. The new replication direction will be maintained, even if the pairs are split. A new pair resync will continue to replicate in the same direction.

Title: Migrate host within the same Hitachi array using raidcom.
 Date: 31-May-2018
 Tags: admin, data migration, move, relocate

Because a volume can be mapped to multiple hosts at the same time, which is done with clustered hosts, migrating volumes from one host to another within the same storage array is a trivial process. Some precaution is required though, to prevent crashing the former host. Note the location where each step is executed, shown in parenthesis.


a) Review SAN storage configuration.

   Identify existing host volume LDEVs, name and size, if any exist.
     # cci-report.sh <serial> ldev <host>

   Identify the HostGroup and pWWNs for this host.
     # cci-report.sh <serial> hostgrp <host>


b) Umount the volumes to be migrated. (old host)

   Make sure all applications that use these volumes have been shutdown prior to unmounting; or, the host has been powered down.


c) Unmap the volumes from the old HostGroup ports. (array management host)

   Delete logical device from HostGroup, using logical device ID.
     # raidcom delete lun -port <port> [<host group name>] -ldev_id <ldev#> -I[Instance#]

   Delete host HBAs from the HostGroup. (if all LUNs have been removed)
     # raidcom delete hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -I[Instance#]

   Delete the Port. (if all LUNs have been removed)
     # raidcom delete host_grp -port <port> [<host group name>] -I[Instance#]


d) Map the volumes to the new host HostGroup ports. (array management host)

   Identify next available Group ID for this HostGroup.
     # raidcom get host_grp -port <port> -I[Instance#]

   Create HostGroup and set mode based on host OS. (skip if HostGroup already exists)
     # raidcom add host_grp -port <port> -host_grp_name <Host Group Name> -I[Instance#]
     # raidcom modify host_grp -port <port> [<host group name>] -host_mode <host mode> -host_mode_opt <option> -I[Instance#]

   Add the host and nickname for the HBAs to the new HostGroup. (skip if HBA WWNs and nicknames already exist)
     # raidcom add hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -I[Instance#]
     # raidcom set hba_wwn -port <port> [<host group name>] -hba_wwn "<WWN_strings>" -wwn_nickname <WWN nickname> -I[Instance#]

   Map logical device to HostGroup, using unique LUN.
     # raidcom add lun -port <port> [<host group name>] -ldev_id <ldev#> -lun_id <lun#> -I[Instance#]

   Verify the new migrated volumes.
     # cci-report.sh <serial> ldev <host>


e) Rename the volumes. (array management host)

   Update each of the logical volume names to with the new hostname and/or application name.
     # raidcom modify ldev -ldev_id <ldev#> -ldev_name <ldev name> -I[Instance#]


f) Validate the migrated volumes on the new host. (new host)

   Re-scan the HBA, so that the OS can now "see" the migrated volumes on the new host.


Notes:

 - The WWNs are formatted differently on the Hitachi array vs. Brocade fabric switches. The colons must be removed when referencing WWNs on Hitachi storage arrays. The script cci-report.sh includes colons for ease of readability, and matching format used by sw-report.sh (the script used to extract SAN fabric information).

 - Unless the hosts are running in a clustered environment, do not mount the same volume on more than one host at a time. Ignoring this may cause one or both hosts to panic, and potential data corruption.

 - Do not unmap (remove volume from Host Group) while the volume is still mounted on a running system. Doing so may generate data corruption as the host is unable to complete writes to disk.

 - On UNIX/Linux systems, update the /etc/fstab or equivalent on both hosts, so that each host sees the correct volumes, ie. the source volumes are no longer visible to the old host, but are configured on the new host.

 - If this change is permanent, consider updating the SAN fabric to reflect these changes.

Title: Change Pool Subscription Limit Hitachi array using HiCommand.
 Date: 06-Feb-2019
 Tags: admin, performance

Dynamic Provisioning monitors pool capacity using thresholds. A threshold is the proportion (%) of the used capacity of the pool to the total capacity of the pool, or the proportion (%) of the physical used capacity of the pool to the total capacity reserved for writing of the pool. When the used capacity of a pool reaches or exceeds the utilization thresholds set for the pool, an alert will be generated.

The subscription limit is the ratio (%) of the total DP-VOL capacity that has been configured to the total capacity of the pool. The limit includes pages required to store user data and control information. The total capacity of DP-VOLs that are created from the pool is always smaller than the subscription limit capacity. 


a) Locate the Pool to change.
   HiCommand > Resources > Storage Systems > [array] > DP Pools > [Pool] > Edit Pool

b) From the Edit Pools window, expand Advanced Options.

c) Update Pool Utilization values.

   Used Threshold 1 = 70% (default warning value)
   Used Threshold 2 = 80% (default depletion value)

d) Update Pool Subscription values.
   Check Subscription Thresholds to enable.

   Warning = (0% - 65534%)
   Limit   = (0% - 65534%)

e) Click Submit to save changes.


Notes:

 - The Depletion Threshold must be higher than the Warning Threshold.

 - If the pool used-capacity is equal to or greater than the Warning or Depletion Threshold, a service information message (SIM) is issued by the storage system. SIMs are displayed by Device Manager - Storage Navigator and other management software and reported to the open-system hosts as SNMP traps.

 - When the subscription limit is set, another DP-VOL cannot be added if the new DP-VOL capacity would cause the subscription limit to be exceeded.

Title: Expanding a Pool using Ops Center
 Date: 13-May-2025
 Tags: admin, expand, grow

To expand a pool (that is, increase the capacity of the pool), add pool-VOLs to the pool.

Note: Only a pool volume created on flash media (SSD) can be added to a pool that includes a DRS-VOL.

- You cannot expand a pool while the pool is being shrunk.

- When you add pool volumes to a Dynamic Tiering pool, tier relocation activities that are in process are stopped.

- When you add pool volumes with available monitoring information to a Dynamic Tiering pool, tier relocation is performed. When you add pool volumes without available monitoring information to a pool, the page usage rate is averaged in the tier.


1. Click Storage Systems, and then expand the Storage Systems tree.

2. Click Pools.

3. From the Pools table or the Pool Volumes tab on which you select the target pool name, select the pool you want to expand. You can expand only one pool at a time.

4. Click Expand Pool.

5. In the Expand Pool window, select the pool-VOL.
   a) Click Select Pool VOLs.

   b) In the Select Pool VOLs window, from the Available Pool Volumes table, select the pool-VOLs you want to add to the pool, and then click Add.

      Pool considerations:

      - The pool can contain up to 1,024 pool-VOLs.
      - For a pool, you can add volumes whose drive types are different and whose RAID levels are different.

      The selected pool-VOLs are registered in the Selected Pool Volumes table.

      Note: If necessary, perform these steps:

      - From Filter option, select ON to filter the rows.
      - Click Select All Pages to select pool-VOLs in the table. To cancel the selection, click Select All Pages again.
      - Click Options to specify the unit of volumes or the number of rows to be viewed.
      - To set the tier rank of an external volume to a value other than Middle, select a tier rank from External LDEV Tier Rank, then click Add.

   c) Click OK.

Title: Create a DP Pool using Device Manager
 Date: 09-May-2025
 Tags: admin

When creating a pool, you will need to select the pool volumes (pool-VOLs) used to create the pool and then set the warning and depletion thresholds. You can also enable options such as V-VOL protection and data deduplication. Before creating the pool, make sure the proper amount of shared memory has been installed. To add shared memory, contact your service representative.


 1. Click Storage Systems, expand the Storage Systems tree, and select Pools.

 2. In the Pools window, click Create Pools.

 3. From the Pool Type list, select Dynamic Provisioning.

 4. For Multi-Tier Pool, select Disable.

 5. If you plan to add external volumes larger than 4 TB to this pool, 
    select Enable for Data Direct Mapping.

 6. For Pool Volume Selection, select Manual.

 7. Select pool-VOLs:

    a) Select a drive type and rpm of pool-VOLs from Drive Type/RPM. 
       If you want to create a DRS-VOL in the created pool, select SSD for the drive type.

    b) From the RAID Level list, select the desired RAID level.
       If you selected External Storage in step a, a - (hyphen) is displayed and you cannot select the RAID level.

    c) Click Select Pool VOLs.

    d) In the Available Pool Volumes table, select the pool-VOLs to be associated with the pool, and then click Add. 
       You can select a value other than Middle from External LDEV Tier Rank and click Add to set another tier rank for an external volume.

       Note: Up to 1,024 volumes can be added including the volumes already in the pool.

    e) In the Select Pool VOLs window, if the selected pool-VOLs have no issues, click OK. 
       The information in the Selected Pool Volumes table is applied to Total Selected Pool Volumes and Total Selected Capacity in the Create Pools window.

 8. In Pool Name, enter the desired name for the pool.

 9. Click Options.

10. In Initial Pool ID, type the number of the initial pool ID. 
    If you specify a pool ID that is already used, the smallest available ID that is the same as or larger than the specified ID is automatically set. If a pool ID is unavailable, no number is displayed.

11. In Subscription Limit, enter the desired subscription rate (%) of the pool.
    To set the subscription limit to Unlimited, leave this field blank, ie. do not enter a number.

12. In Warning Threshold, enter the desired warning threshold (%) for the pool.
    If the pool used-capacity is equal to or greater than the warning threshold, a service information message (SIM) is issued by the storage system. The default threshold is 70%.

13. In Depletion Threshold, enter the desired depletion threshold (%) for the pool.
    Enter a value that is equal to or greater than the warning threshold. If the pool used-capacity is equal to or greater than the depletion threshold, a SIM is issued by the storage system. The default threshold is 80%.

14. In Suspend TI pairs when depletion threshold is exceeded, select Yes or No.
    This option enables you to stop the Thin Image pair split process and prioritize the writing process to DP-VOLs when the free capacity of a Dynamic Provisioning pool that contains Thin Image pairs and snapshot data is depleted.

    If you select Yes, SIM code 62Exxx is output when the pool used capacity exceeds the depletion threshold. After this SIM code is output, if you split a Thin Image pair in the depleted pool, the operation fails, and the pair is suspended by error (PSUE).

    This option is not available for Thin Image Advanced pairs.

15. In Protect V-VOLs when I/O fails to Blocked Pool VOL, select Yes or No. 
    If Yes is selected, when the pool-VOL is blocked, DP-VOL is protected from reading and writing requests. And at the same instant, the access attribute of the DP-VOL is changed to the protect attribute.

    This option applies only to DP-VOLs that do not include DP-VOLs with capacity saving enabled. This option does not apply to V-VOLs used by Thin Image pairs.

16. In Protect V-VOLs when I/O fails to Full Pool, select Yes or No. 
    If Yes is selected, when the pool usage reaches the full size, DP-VOL is protected from reading and writing requests. And at the same instant, the access attribute of the DP-VOL is changed to the protect attribute.

    This option applies only to DP-VOLs. It does not apply to V-VOLs used by Thin Image pairs.

    Caution: If you create a DP pool of which the NAS-Unified-Firmware is to be installed, select No in this option.

17. Click Add to add the specified pool to the Selected Pools table. 
    If invalid values are set, an error message is displayed. The Pool Type, Pool Volume Selection, and Pool Name must be set. If these required items are not entered or selected, you cannot click Add.

    To view the detailed properties of a pool in the Selected Pools table, select the pool and click Detail. To remove a pool from the Selected Pools table, select the pool, click Remove, and then click OK.

18. If you want to create DP-VOLs in the new pool, click Next.
    If Subscription Limit of the specified pool is set to 0%, an error message is displayed and the Create LDEVs window is not displayed. If you do not want to create DP-VOLs in the new pool, click Finish and proceed to the next step.

19. In the confirmation window:

    a) Confirm the settings.

    b) Accept the default task name or enter a unique name.
       You can enter up to 32 letters, numbers, and symbols.

    c) Click Apply. 
       If you want to view the list of tasks for the storage system, select Go to tasks window for status. To view the detailed properties of a pool, select the pool and then click Details.

20. Click Apply to submit the task.

Title: Changing the storage IP address on the Hitachi VSP G1500.
 Date: 09-Sep-2025
 Tags: admin

When the array needs to move to a new IP address due to a subnet change, the network information on the SVP will need to be updated. This requires a network change in two places, the Public LAN as defined in Windows Network Connections, and Master SVP address within the Maintenance Components from Device Manager.

a) Collect the Internal LAN IP address.
   Use this address as a backup in case you're unable to connect using the new IP.

   Open the Network Connections window.
   From the Taskbar click Network Connections.

   Open the Internal LAN Properties window.
   Select Internal LAN > Properties > Internet Protocol Version 4 > Properties

   Record the IP Address and Subnet Mask.
   This will be unique for each storage array.

   Return to Network Connections.
   Click Cancel button to close each window.


b) Change the Public LAN IP address.
   This will be the new IP address used to access the storage array.

   Open the Public LAN Properties window.
   Select Public LAN > Properties > Internet Protocol Version 4 > Properties

   Enter the new IP Address and Subnet Mask.
   This should be unique for each storage array.

   Save the new network configuration.
   Click OK button.

   Close all of the network related windows.


c) Change the storage IP and subnet of the Hitachi array.
   This should match the new Public LAN IP address previously set.

   Open Maintenance Components window.
   From Device Manager select Maintenance > Maintenance Components

   Enable Modify mode to enable configuration changes.
   Click the View Mode button.

   Go to the Set IP Address window.
   Select Install > Set IP Address

   Set the Master SVP address.
   Enter the new IP Address and Subnet Mask, then click OK button.

   This will cause the SVP to reboot and start using the new IP address.


d) Revert back to the original IP address.
   Use these steps if you're unable to communicate using the new IP address.

   Change the IP address and Subnet Mask on your laptop.
   Use the same Subnet Mask and IP defined in the Private LAN, but with a different value in the last IP octet.

   Connect to the storage array using the Internal LAN IP address.
   Use Remove Terminal Desktop after connecting network cable from laptop to array.

   Set the original IP Address and Subnet Mask.
   Follow steps shown in (c).
